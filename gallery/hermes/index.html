Hermes Agent: who decides what

Read the one-page summary first · The gallery · Make a map of your own system · The repository

The Hermes agent and the judgments it makes while running: who may send it work, what the model sees, which tool runs next, which actions need a person's approval, limits and compression, judging the result, delegation, and what it learns. Read in NousResearch/hermes-agent at commit b200f5bc. The messaging platform adapters are read as one family; the desktop and terminal interfaces, packaging, and optional plugins that are off by default are outside this map, except where they answer a question the agent asks. Claims about how the code behaves refer to that commit. The project is MIT-licensed; this page quotes short identifiers and cites files and lines at that commit.

How to read this page

A seat is a judgment the agent makes over and over: may this sender's message run, what goes in the prompt, may this command run, is the turn over. Each card records the question, how it is answered, and who or what holds it, with the code that implements or exposes that decision. Seat ids (A1, B11 …) are links.

Each answer describes what Hermes does at its default settings: the code's defaults plus the config.yaml the installers start from, a copy of the repository's cli-config.yaml.example. Running hermes setup or editing config.yaml changes some of these; where an answer depends on such a value, it names the setting. Platforms and opt-in plugins that change an answer are named where they matter; exceptions named are the main ones, not a complete list.

The chip on each card has two words. The first is about the question: a RULE has one right answer given its inputs, so a run that answers differently is a bug; a RULING is one that competent people could answer differently. Enforcing a limit someone set is a RULE; choosing what to keep, what to trust or when the work is done is a RULING, even when code holds it.

The second word is who holds it: llm = a language-model call; model = another learned model; code = code in the repository; human = a person; external = code outside the repository that the agent hands the decision to.

Paths are from the repository root. A bare :120-140 or (323) means lines in the file named just before it.

A1 May this sender's message dispatch agent work? RULE · code
Answered how

Code walks a fixed order of grants on every inbound gateway message (_principal_authorized): a local session is decided by its own adapter, webhook and trusted-inbound platforms pass, then chat-scoped grants, per-platform allow-all, role auth, the pairing store and the env/config allowlists. With no allowlist configured and GATEWAY_ALLOW_ALL_USERS unset (the fresh-install case), an unknown sender is denied unless an operator approved their pairing code. A bot-authored message that passes is still refused while its chat's loop guard is cooling down.

Held by

A2 Does an unrecognised DM sender get a pairing code, silence, or a decline? RULE · code

On a fresh install with no allowlist the global default is pair, so the stranger gets a pairing code with the approve command; an ignored sender triggers one notice per sender per process to the owner's home channel, if one is set.

A3 Should this stranger be let in? (pairing approval) RULING · human
Answered how

A person answers: the stranger is sent a code and the operator decides by running hermes pairing approve <platform> <code>; code then records the approval and, if an allowlist env var is configured, adds the user to it. Code bounds the question: codes expire after one hour, at most 3 are pending per platform, and 5 failed approvals lock the platform out for an hour. This only arises when the DM behaviour is pair, which is the default with no allowlist.

A4 In a group chat, is this message addressed to the bot? RULE · code
Answered how

A8 While the agent is busy, does a new message interrupt, queue, steer or redirect the run? RULE · code
Answered how

Code applies the configured display.busy_input_mode, which defaults to interrupt. In interrupt mode a plain-text message redirects the running turn when the running agent supports redirect, and the mode is demoted to queue while subagents are running or context compression is in flight; in steer mode the text is injected into the running turn, falling back to queue when it cannot be steered; in queue mode the message waits for the turn to end.

Held by

A10 Should a scheduled job wake the model at all this run? RULING · external
Answered how

Only for a scheduled job that has a pre-run script. The script, which the user wrote, decides: if the last non-empty line of its output is the JSON {"wakeAgent": false}, the run is skipped with no model call and no delivery. Answered how

Code assembles it in a fixed order of three tiers: stable (identity, help and model guidance, pinned skills, the coding brief), context (the caller's system message, project context files, the workspace snapshot), then volatile (skills index, memory, plugin sections, profile line, timestamp, runtime environment hints).
