DeerFlow: who decides what

Read the one-page summary first · The gallery · Make a map of your own system · The repository

The DeerFlow agent harness (its Python harness package and the gateway, channel and scheduler code that answers the harness's requests) in bytedance/deer-flow, read at commit 14abd9a2 (2026-11-02). Claims about how the code behaves refer to that commit. Their code is MIT-licensed; this page quotes short identifiers and cites files and lines at that commit.

How to read this page

A seat is a judgment the agent makes over and over: which model runs a turn, what the model sees, may this tool call run, is the work done. Each card records the question, how it is answered, and who or what holds it, with the code that implements or exposes that decision. Seat ids (A1, D12 …) are links.

Each answer describes what DeerFlow does by default at the commit named above. Exceptions named are the main ones, not a complete list.

The chip on each card has two words. The first is about the question: a RULE has one right answer given its inputs, so a run that answers differently is a bug; a RULING is one that competent people could answer differently. Enforcing a limit someone set is a RULE; choosing what to keep, what to trust or when the work is done is a RULING, even when code holds it.

The second word is who holds it: llm = a language-model call; code = code in their repository; human = a person; external = something outside the repository that the agent hands the decision to (a hosted service, a sandbox provider, a configured command).

Paths are relative to the repository root. A file name written without its folder is in the folder of the full path written before it on the same card. A bare :120-140 means lines in the file named just before it.
