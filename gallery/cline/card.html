How Cline decides

In an ordinary Cline session, plain code runs the work and sets its limits, and the AI model decides when the task is done. By default the model also writes the summary that replaces older history, and in interactive command-line plan mode it decides when to start acting on the plan.

From cline/cline at source version d19f176b, mapped 2026-11-02. Each answer links the place in the code where that decision is made; the full map has the rest.

What it does without asking you

  • On the command line, do tool calls run without asking you?

    Decided by plain code By default, yes. At startup code sets one policy for all tools from the --auto-approve or --yolo flag if given, else your saved setting, else on, so out of the box tool calls run without asking, in ordinary sessions as well as yolo mode.

    main.ts:885-895 · decision D4 in the full map

How it decides it is done

  • How does it decide the task is finished?

    Decided by an AI model In an ordinary session, the model replies without asking to use a tool and code ends the run as completed; nothing checks that the work was done.

    agent-runtime.ts:952-974 · decision G1 in the full map

  • When its yolo mode ends a run as "verified", does anything check?

    Decided by an AI model No. The model ends the run by submitting a summary with a verified yes or no, and both the command-line tool and scheduled runs accept the submission either way.

    approval.ts:166-172 · decision G2 in the full map

  • Did a scheduled run succeed?

    Decided by plain code Unless the run was cancelled, timed out or lost its place, any turn that does not end with an error, including one that ended as stopped, is recorded as done and counted as a success.

    cron-runner.ts:445-485 · decision G5 in the full map

Limits and memory

  • How long can it keep going before it is stopped?

    Decided by plain code Ordinary VS Code and command-line sessions set no limit on steps. A time limit applies only where a caller sets one, such as the --timeout flag on a one-shot run or a schedule.

    agent-runtime.ts:839-842 · decision F5 in the full map

  • When the history gets too long, who decides what to keep?

    Decided by an AI model With the default strategy, a model writes a summary of the older part while about the last 20,000 tokens stay word for word, and code puts in place any summary that is not empty.

    agentic-compaction.ts:189-235 · decision F7 in the full map

Other judgments

  • In VS Code, may this shell command run?

    Decided by a person When a command reaches the approval step and neither its policy nor the auto-approve toggle for commands (off by default) approves it, code shows an Approve or Reject row and waits for the person. Only Approve lets that command run; a typed message leaves the question open.

    sdk-interaction-coordinator.ts:118-280 · decision D3 in the full map

  • In plan mode on the interactive command line, who decides you have approved the plan and the work can start?

    Decided by an AI model The model, by calling a switch-to-act tool; the tool does not look at what you wrote. When that turn completes, the command-line tool rebuilds the session in act mode and starts on the plan. The call itself follows the command line's approval setting.

    mode.ts:31-68 · decision A3 in the full map

Three problems in the code

  1. 1. Shell commands are cut off at 30 seconds

    On the command line, a shell command the agent runs gets 30 seconds by default; then code tries to kill it and the agent is told it timed out, so a long build, test run or install can be stopped partway. Cline's tracker has two open reports about this limit.

    Already tracked upstream (#10549), checked 2026-11-08.

    Where: bash.ts:829-843, bash.ts:1138, definitions.ts:515. How we checked: the code was re-read at the source version named above; the sentences were checked by an independent AI reviewer from another company (OpenAI Codex, read-only) on 2026-11-08, in four rounds; each sentence it questioned was narrowed, removed or kept with the reason recorded.

  2. 2. A file edit that timed out can still be written

    File edits are given a time limit, but reaching it only tells the model the edit failed; the edit itself is not stopped. So the model can be told an edit timed out while the change still lands in the file. An open report in Cline's tracker describes the same outcome in VS Code: a timeout reported after the write had landed.

    Already tracked upstream (#13267), checked 2026-11-08.

    Where: definitions.ts:745-749, helpers.ts:49-60, editor.ts:230-267. How we checked: the code was re-read at the source version named above; the sentences were checked by an independent AI reviewer from another company (OpenAI Codex, read-only) on 2026-11-08, in four rounds; each sentence it questioned was narrowed, removed or kept with the reason recorded.

  3. 3. A cut-off summary is used as if it were complete

    When the default strategy shortens the history, the model's summary replaces the older messages. If the summary was cut off before the model finished it, code still puts it in place; only an empty reply is skipped.

    Reported; a fix is proposed, not merged (#14741), checked 2026-11-08.

    Where: agentic-compaction.ts:189-235. One problem was also tested by running it: a file edit that timed out. On 2026-11-12, at this commit, Cline's editor tool was given a 50 ms limit around its real file editor. The test delayed that editor on purpose before it started. The tool reported that the edit had timed out while the file was still unchanged, and the file changed once the editor finished. In separate cases of the same test, a normal edit landed and reported success, and an edit made to fail before writing left the file unchanged. No model was used, and the test does not show how often a real edit is that slow. The reproduction covers only the three cases described here.
