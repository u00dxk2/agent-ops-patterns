browser-use's Agent at its defaults (the step loop, what the model sees, the actions it can take, the browser session's watchdogs, limits and the final judgment), in browser-use/browser-use, read at commit b49a68e4. Separate entry points (the beta agent, the sandbox runner, the MCP server and the command line) are outside this map, and so are Browser Use's cloud browsers and other features that are off until a setting turns them on. Claims about how the code behaves refer to that commit. Their code is MIT-licensed; this page quotes short identifiers and cites files and lines at that commit.

What will it click or submit on its own, and what stops it?

Nothing asks first. The model's chosen actions run as soon as they are parsed, so no person approves a form submit, a purchase or a page script D17. The ordinary built-in actions are offered on every page, evaluate among them, which runs JavaScript the model writes B10.

Some page events are answered by code before the model sees them: it clicks OK on alerts and confirm dialogs the moment they open D7, grants clipboard and notification permissions to every site D8, and saves offered PDFs and attachments without a click D9.

A run normally ends when the model calls done G1. The automatic stops are counts, not judgments: 500 steps F1, or 5 failed steps in a row followed by one last forced answer F5. On Mac and Linux a person at the terminal can pause it with Ctrl+C; on Windows the first press quits D18. An integrator who wants an approval step adds it in their own code, through the step callback D17.

How to read this page

A seat is a judgment the agent makes over and over: what the model sees of the page, which action runs next, may this page be opened, is the task done. Each card records the question, how it is answered, and who or what holds it, with the code that implements or exposes that decision. Seat ids (A1, B12 …) are links.

Each answer describes what browser-use does by default. Exceptions named are the main ones, not a complete list.

The chip on each card has two words. The first is about the question: a RULE has one right answer given its inputs, so a run that answers differently is a bug; a RULING is one that competent people could answer differently. Enforcing a limit someone set is a RULE; choosing what to keep, what to trust or when the work is done is a RULING, even when code holds it.

The second word is who holds it: llm = a language-model call; model = another learned model; code = code in their repository; human = a person; external = code outside the repository that the agent hands the decision to.

Paths are relative to the repository root. A bare :120-140 or (323) means lines in the file named just before it.

How this map was made

Four readers each took a part of the agent and wrote seat cards from the source, and four more rewrote each answer in a short form that describes the default.
